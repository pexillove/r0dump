# R0DUMP 移植指南

> 中文 · [English](../en/PORTING.md)

本指南说明如何基于已发布的 Android 16 Fusion 补丁集完成可复现的设备与 ROM 移植。不同源码树之间存在差异，请逐项完成文中的构建和真机验证。

> [!WARNING]
> OnePlus 9 官方镜像只能刷入对应设备。其他设备必须基于自身 ROM 和设备树重新构建，并在可恢复的测试设备上验证。公开仓库不得包含专有二进制文件、签名密钥、设备备份、应用数据或受保护的第三方代码。

## 1. 记录移植基线

修改代码前，先在移植仓库中记录以下信息：

| 项目 | 必填内容 |
|------|----------|
| 设备 | 产品名称、产品代号、设备代号、SoC、支持的 ABI |
| ROM | 项目、分支、Android 版本与 SDK、清单版本 |
| R0DUMP | 补丁集版本或标签，以及移植后产生的提交 |
| 构建 | 产品目标、`lunch` 目标、主机环境要求、签名方式 |
| 恢复 | 可用的原厂包、Recovery 或 Fastboot 恢复路径、回退步骤 |
| 验证 | 已完成构建、刷写和真机测试的具体范围 |

固定源码清单以及所有受影响仓库的版本。使用“最新版本”无法形成可复现基线。

## 2. 从 Fusion 基线开始

当前上游补丁位于 [`patches/v2026-09-12-fusion/`](../../patches/v2026-09-12-fusion/README.md)：

| 补丁组 | 上游基线 | 作用 |
|--------|----------|------|
| `art/` | AOSP 标签 `android-16.0.0_r4` | 捕获点、主动调用流程、DEX 证据与重建 |
| `frameworks_base/` | LineageOS `lineage-23.2` | 配置路径、任务编排、限定范围的输出准备 |
| `system_sepolicy/` | LineageOS `lineage-23.2` | Manager、辅助程序域与受限导出策略 |
| `packages_apps_R0dumpManager/` | 新仓库，根提交补丁序列 | Manager 界面、辅助程序、修复与导出、内嵌 MCP 桥 |
| `vendor_lineage/` | LineageOS `vendor/lineage` | 可选的版本显示标识 |

每个目录中的补丁按文件名顺序应用。已有提交历史的仓库使用 `git am`，供应商标识文件为普通差异文件，使用 `git apply`。准确命令以 [Fusion 补丁说明](../../patches/v2026-09-12-fusion/README.md)为准。

处理移植冲突时，记录以下内容：

- 上游文件和版本；
- 原补丁的目标；
- 移植后的实现；
- 能够证明目标仍然成立的构建或运行证据。

## 3. 集成 Manager 与产品配置

移植后的 `packages/apps/R0dumpManager` 必须作为源码项目加入产品构建。请核对：

- Manager 项目已加入源码清单，并从源码参与构建；
- 包名、特权权限、平台签名和产品包含关系符合补丁约定；
- Framework、Manager、本地辅助程序和 SELinux 策略使用相同协议与路径；
- 最终镜像包含 R0DUMP 系统属性和配置文件；
- 版本显示改动保持可选，不影响功能集成；
- 正式签名密钥存放在公开仓库之外。

## 4. 适配设备和 ROM 差异

以下内容需要单独适配和验证：

1. **架构**：为设备实际运行的全部 ABI 构建 ART 改动，例如 ARM64 系统上的 ARM32 应用支持。
2. **存储**：核对目标 ROM 的模拟存储挂载方式，以及 Manager 使用的固定公开导出路径。导出失败时保持明确报错，避免回退到范围过大的私有或 root 可写目录。
3. **SELinux**：保持 Enforcing。围绕现有的 Manager → Framework → 辅助程序调用关系添加最小策略；Permissive 结果不能作为验收证据。
4. **进程生命周期**：验证冷启动、次要进程、不同 Zygote 以及应用重启；任务结束后不得留下意外启用的捕获状态。
5. **资源预算**：根据设备性能调整遍历、调用、时间和输出限制，同时保留停止条件与 ANR 保护。
6. **ROM Framework 差异**：重新核对 ActivityManager、存储钩子、特权权限声明和隐藏 API 访问。
7. **OTA 与回退**：记录被替换的分区、用户数据保护方式，以及恢复到已知可用构建的步骤。

## 5. 构建检查

至少记录以下项目的最新结果：

- 受影响的 ART 主机测试和修复工具测试；
- 移植补丁中包含的 Manager 单元测试与仪器测试；
- SELinux 策略构建、`neverallow`、映射和兼容性检查；
- 覆盖全部受影响模块的完整产品构建；
- 在固定版本的干净源码树上复现补丁和覆盖文件；
- 发布压缩包完整性与密码学校验值。

单个模块构建成功只能证明该模块通过编译。启动镜像、系统镜像、策略、Manager 和运行时协议仍需一起验证。

## 6. 真机验收

只使用已经获得授权的测试样本。保留日志时不得上传受保护代码。移植项目的验证状态应严格对应已经完成的检查项。

- [ ] 设备在 SELinux Enforcing 状态下启动，且没有新增的持续崩溃循环。
- [ ] 当前运行的 Manager APK 与策略文件来自同一份受测构建。
- [ ] Manager 能列出应用、接受有边界的配置，并且只为选定目标启用捕获。
- [ ] 冷启动目标后产生一个可识别的任务，并遵守停止限制。
- [ ] 测试样本支持时，分别覆盖标准 DEX 与内存 DEX 路径。
- [ ] “修复并导出”通过稳定的任务标识选择正确任务。
- [ ] 导出的 ZIP 与 `.sha256` 校验文件验证成功。
- [ ] 修复后的 DEX 通过目标 Android 版本的 `dexdump`，并可使用 JADX 检查。
- [ ] 重启、禁用、失败和无输出路径均保持设备可恢复。
- [ ] 日志不包含私钥、应用数据、专有二进制文件或重新分发的受保护内容。

报告结果时注明准确数量和工具版本。例如，“5/5 个修复后的 DEX 通过 Android 16 `dexdump`”可以界定验证范围。

## 参考移植项目

[`yruh/r0dump-redmi9a-crdroid16`](https://github.com/yruh/r0dump-redmi9a-crdroid16) 是当前收录的首个移植案例。该项目将 R0DUMP 移植到 Redmi 9A（`blossom` / `dandelion`）的 crDroid 12.11 / Android 16，并提供固定的源码清单、各仓库补丁、覆盖文件、应用与验证脚本、构建文档及真机证据。

该仓库可用于参考目录组织方式和证据记录格式。其他设备仍需根据自身源码基线完成移植。

## 提交社区移植

在 README 的“社区移植”区域申请收录前，请提交 Issue 或 PR，并提供：

- 公开仓库地址、维护者和许可证；
- 设备、SoC、ABI、ROM、Android 与 SDK 版本、构建目标；
- 固定的源码清单、基础版本与 R0DUMP 补丁集版本；
- 在干净源码树上应用补丁并完成构建的步骤；
- 已完成的构建、刷写、DUMP、修复、ZIP、校验值、`dexdump` 与 JADX 验证；
- 已知限制、回退方式和安全警告；
- 仓库不包含专有二进制文件、私钥、设备备份、用户数据或受保护第三方代码的声明。

建议使用以下表格：

```markdown
| 设备 / ROM | 维护者 | 状态与证据 | 源码 |
|------------|--------|------------|------|
| 设备（代号）· ROM · Android | @name | 可复现构建；已完成的真机检查：…… | [仓库](https://github.com/...) |
```

移植项目由各自作者维护和提供支持。README 收录只记录公开证据，不改变项目的维护归属。
